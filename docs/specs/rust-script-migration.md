## 2. 目标与范围

### 背景与目标

旧 shell 已封存到 [legacy/box-scripts](../../legacy/box-scripts/)，不再随模块安装或运行；运行职责由 Rust `boxctl` 承担。1.4.0 的 `settings.ini` 是含数组、函数与运行期操作的可执行 Shell；当前 2.0.0 主线已改为 [settings.json](../../box/settings.json) + [settings.schema.json](../../box/settings.schema.json)，并由 Rust `boxctl` 直接加载/校验 `settings.json`；旧 shell 已封存到 `legacy/box-scripts/`。本迁移以 2.0.0 为基线，不回到可执行设置。

本次目标是可靠性、可维护性优先的 Rust 主控制器：Shell 仅保留必要的平台入口；Rust 直接调用 Linux/Android 工具，不因需要运行命令就额外经过 Shell。用户明确接受破坏性更新，拒绝为旧接口、旧配置执行格式维持长期桥接。2.0.0 起仅保留 mihomo，sing-box 配置和运行分支不再迁移。

### 本次文档重写范围

- 目标：把现有迁移草稿整理为可实施、可验收、可追踪的开发规格，消除过时假设和跨规格冲突，补齐架构、接口、状态、测试、实施阶段与发布门禁。
- 非目标：不在本文档中写 Rust 代码、不运行模块脚本、不部署、不提交或推送 Git；不重新决定已确认的 D-001–D-022 产品行为；不把新设计 D-023–D-026 冒充已验证实现。
- 完成标准：七个必需章节与第 8 节结构完整；R 与 AC 双向覆盖；编号唯一；链接/表格/状态合法；未决项与验证缺口明确；实现状态和验证状态保持真实。
- 本文档的“完成”是规格完成，不是产品迁移完成。

### 本次迁移范围

- 迁移已封存的 [box.tool](../../legacy/box-scripts/box.tool)、[box.service](../../legacy/box-scripts/box.service)、[box.iptables](../../legacy/box-scripts/box.iptables)、[net.inotify](../../legacy/box-scripts/net.inotify)、[box.inotify](../../legacy/box-scripts/box.inotify)、[ctr.utils](../../legacy/box-scripts/ctr.utils) 和 [start.sh](../../legacy/box-scripts/start.sh) 承担的运行控制职责。
- 统一为计划部署在 `/data/adb/box/bin/boxctl` 的一个 Rust 二进制，提供常驻管理进程与轻量 CLI。
- 更新 [WebUI](../../webui/src/main.tsx)（2.0.0 的 TypeScript/React 版本）、安装/卸载/启动衔接、内建任务、测试、构建发布和文档中的受影响调用方。
- 继续以 `settings.json` 保存模块设置，以 `settings.schema.json` 为目标字段契约；但当前 2.0.0 运行期未实际读取 schema，实际校验在 `box.tool` 手写代码，Rust 必须补齐 schema 与手写校验的差异，不能声称“复用现有 schema 校验器”。代理核心仍使用自己的 YAML 等格式，源配置与生成运行配置分离。Rust 不引入 TOML，也不维护第二套配置源。
- 保留成熟系统工具与代理核心。Rust 可以直接调用 `iptables`、`ip6tables`、`ip`、`ipset`、`boxbpf`、`getprop`、`cmd wifi` 等；不在首阶段重写内核网络接口。
- 首个内部试点为配置与设置 CLI，先面向 Android arm64；完整运行路径完成后才进行整体破坏性切换。

### 非目标与当前授权边界

- 不重写代理核心本身，也不新增承载管理接口的 HTTP 服务。
- 不提供旧脚本命令路径或旧 `{ok,data,error}` JSON 契约适配；最终不生成 Shell 配置快照，不维护双配置源。2.0.0 的 `settings.runtime.sh` 仅作为完整切换前现有 Shell 入口的临时运行文件，完整切换时移除。
- 不导入旧 `settings.ini` 的可执行值；现有 `settings.json` 按 D-019 做 root-only 备份后重置为 2.0.0 默认值并置 `boot_auto_start=false`，token 按 D-022 备份后清除，不视为导入。
- 不再执行用户旧定时文件中的任意 root Shell 行。
- 不将“重置旧模块设置”扩大为删除全部用户数据。settings.json/githubtoken 的备份后重置/清除是明确例外；核心源数据保留，旧独立名单明确丢弃，具体边界见 R-014；普通卸载与完整清除见 R-015。

## 4. 行为要求与约束

### R-001：统一管理进程与轻量 CLI

- 参与者或触发方：用户、WebUI、Root 生命周期入口、网络事件、内建任务。
- 前置条件与输入：安装了同一版本的 `boxctl`；调用方提交管理请求或事件。
- 必须满足的行为：同一个二进制提供常驻管理和 CLI；客户端通过本地 Unix socket 请求管理进程。管理进程是运行状态变更的统一协调者，协调服务、规则和后台任务。Root 模块启用时管理 daemon 随系统启动；`boot_auto_start` 只控制代理核心自启，不关闭管理控制面。
- 输出或状态变化：返回请求结果和可解释的运行状态。代理流量仍由代理核心处理；管理器不转发流量、不新增 HTTP 管理服务。
- 边界与失败行为：并发入口不得绕开协调器同时改变同一状态；IPC 与管理进程失效的 v2 行为见 D-023/第 8 节，具体状态机仍见 Q-006。

### R-002：必要 Shell 入口与直接命令调用

- 参与者或触发方：Root 管理器和 Rust 的平台/网络适配模块。
- 前置条件与输入：平台入口、经过校验的命令参数与设备环境。
- 必须满足的行为：[customize.sh](../../customize.sh)、[uninstall.sh](../../uninstall.sh)、[box_service.sh](../../box_service.sh) 等确有平台要求的入口可保留薄 Shell；业务流程迁入 Rust。Rust 以独立参数调用外部命令，不靠拼接 `sh -c` 执行业务流程。
- 输出或状态变化：统一收集退出状态和诊断信息；保留 `iptables-restore` 等批量下发能力，不退化为每条规则启动一个进程。
- 边界与失败行为：系统工具缺失、权限失败、超时及非零退出必须可诊断；是否保留某个启动包装文件不代表保留其旧运行接口。

### R-003：settings.json 备份/重置、升级确认与破坏性切换

- 参与者或触发方：全新安装、升级准备和升级后的首次核心启动。
- 前置条件与输入：设备可能有 1.4.0 的旧 `settings.ini`，以及 2.0.0 的 `settings.json`、`settings.schema.json` 和独立 `githubtoken`。
- 必须满足的行为：
  - 2.0.0 基线不再使用可执行 `settings.ini`；从 1.4.0 直接升级时，先按现有 2.0.0 安装路径备份旧 `settings.ini` 并生成默认 `settings.json`，不执行、不解析、不导入旧 Shell 值。
  - 对现有 `settings.json`：先做 root-only 备份，备份成功后再重置为 2.0.0 的默认值，并将 `boot_auto_start` 置为 `false`；其余默认保持当前产品值。用户需要重新配置。备份失败时不得重置，升级中止并报错。
  - 对独立 `githubtoken`：先做 root-only 备份，备份成功后再清除；CLI/WebUI 只暴露是否已配置，日志不得泄露令牌；备份失败时不得清除。
  - 新安装与升级后的代理核心开机自启均默认关闭；其他初始设置沿用当前产品默认值（见第 8 节默认值基线），但不恢复已废除的设置/任务执行方式。
  - 升级后在用户检查并确认新配置前，不允许首次手动或自动启动代理核心；此迁移确认门槛不额外施加于全新安装。daemon 仍随系统启动。
  - `settings.json`/token 备份限制为 root-only，保留到用户显式完整清除；不生成长期 Shell 快照，不保留设置合并或旧 JSON 适配路径。
- 输出或状态变化：用户需重新设置模块选项并重新配置下载令牌；旧文件仅作为受保护的备份，不是配置源。除 `boot_auto_start=false` 外，默认行为参照 2.0.0 的 `settings.default.json`，例如核心 mihomo、网络模式 TUN、IPv6 开启、Wi-Fi 自动控制关闭、CNIP 绕过关闭；周期任务默认关闭（`run_crontab=false`），即使订阅更新选项本身默认开启。
- 边界与失败行为：旧 `settings.ini` 中的动态代码不是迁移器执行对象，旧个人值不导入；`settings.json` 的重置只允许在备份成功后进行。关闭自启不等于禁止用户在模块启用、迁移确认完成且配置有效时显式启动核心。升级数据处置见 R-014，普通卸载和完整清除见 R-015。

### R-004：手动控制优先于 Wi-Fi 自动控制

- 参与者或触发方：用户服务命令、Wi-Fi/网络事件、Root 模块开关。
- 前置条件与输入：已配置的控制方式与观察到的网络状态。
- 必须满足的行为：显式手动 `start`/`stop` 进入手动控制；只有用户显式切回自动模式，Wi-Fi 策略才可决定启停。手动/自动控制方式与 `tun`/`tproxy` 等代理网络模式正交。手动/自动模式及最后的期望启停状态跨 daemon、设备重启持久化。
- 输出或状态变化：能够解释当前由谁控制服务、期望状态与实际状态。
- 边界与失败行为：网络事件不能覆盖手动停止，未知状态重试也不能越过模块禁用、迁移确认或人工处理门槛。Root 模块禁用时停止核心并清理本模块规则，但不把已保存的期望状态改写成用户手动停止。设备启动或模块重新启用时，`boot_auto_start=false` 保持核心停止；为 true 时，手动模式恢复最后期望状态，自动模式重新评估当前 Wi-Fi。Wi-Fi 暂时未知时保持当前服务状态并有限重试，不等同于已断开。自动启动门槛不禁止有效的显式用户启动；daemon 重启须先核对真实状态，不盲目重复拉起核心。事件源与重试时机见 Q-008。

### R-005：保存配置与确认应用分离

- 参与者或触发方：WebUI 或 CLI 用户保存影响运行服务的设置。
- 前置条件与输入：新的模块设置或核心源配置，以及当前运行版本。
- 必须满足的行为：保存并校验后，标记需要应用的变更；WebUI 询问是否现在应用。用户确认后，管理器才协调受控切换：先校验候选配置/二进制并保留旧有效配置与核心版本，再进行必要的停启、规则变更和健康检查；失败尝试恢复旧有效版本。接受短暂中断，首版不要求跨核心热重载或蓝绿切换；热重载仅可作为后续证明安全的优化。CLI 明确区分保存与应用，不要求后台调用进行交互式确认。
- 输出或状态变化：区分已保存、待应用和已生效；取消立即应用时服务保持原有效版本，只有健康检查成功才标记新版本生效。
- 边界与失败行为：保存成功不等于应用成功；候选校验必须发生在打断健康服务之前。候选无效时健康服务保持当前版本并明确显示错误，已停止服务不得使用无效候选启动，不静默选择其他版本来宣称成功。应用失败报告阶段与恢复结果；切换及回滚均失败时停止受管理核心、尽力清理本模块规则、保留源配置/诊断日志并标记需人工处理，禁止无界自动重试。准确事务顺序及健康判据见 Q-006。

### R-006：核心源配置与生成运行配置分离

- 参与者或触发方：用户编辑、核心启动、模式切换和配置应用。
- 前置条件与输入：用户核心源配置、模块设置及所需资源。
- 必须满足的行为：用户/WebUI 主动编辑才修改源配置；启动和模式切换不回写源文件。Rust 在运行副本中调整模块管理的端口、TUN、入站、UID 等字段，生成候选配置，执行适用的核心校验后才进入应用。
- 输出或状态变化：用户源配置与已生效运行配置分别可识别；保留上一有效运行版本以便恢复。
- 边界与失败行为：生成或校验失败不替换有效配置。运行副本须正确解析 provider、规则集、日志和其他资源路径；文件原子替换不等于整个核心/规则切换原子完成。

### R-007：必需网络操作失败回滚，可选能力显式降级

- 参与者或触发方：服务启动/停止、网络事件、设置应用和能力探测。
- 前置条件与输入：网络模式、IPv4/IPv6 需求及设备能力。
- 必须满足的行为：必需路由/规则失败时回滚部分状态并报错；可选特性只能按明确策略降级/关闭并告警，不静默跳过。应用和清理须幂等，避免残留规则反复叠加。
- 输出或状态变化：区分成功、有效降级和失败，显示实际生效能力；必需步骤未成功不得返回完整成功。
- 边界与失败行为：覆盖六种模式的有效路径，包括不应创建模块网络规则的分支。回滚仅处理本模块拥有的资源，不能通过清空系统规则掩盖失败。必需步骤及回滚均失败时停止受管理核心、尽力清理本模块资源、保留源配置和诊断日志并标记需人工处理；停止自动故障循环，事件/监督器不得绕过此状态无限重试。停止和尽力清理不保证清理成功，也不保证网络断开、流量不直连或 fail-closed；本规格未承诺 kill switch。eBPF、ipset 等可选网络能力在设备能力不足、内核不支持或 `boxbpf` 不可用时，必须按显式策略降级并告警；不得在 API 24 上宣称 eBPF 可用（见 R-013/D-020）。精确恢复顺序见 Q-006。

### R-008：Rust 原生 HTTP 与标准 TLS 校验

- 参与者或触发方：订阅、Geo、核心或其他模块维护下载。
- 前置条件与输入：下载源、认证信息、目标类型与目标文件。
- 必须满足的行为：使用 Rust 原生 HTTP 客户端，正常校验证书；不保留 curl/wget 自动回退或默认跳过证书校验。Rust 负责超时、响应校验、临时文件、内容验证和安全替换。下载认证令牌与普通设置分离，存入独立 root-only 凭据文件；升级迁移按 D-022 先备份再清除旧 token，CLI/WebUI 只暴露是否已配置状态；新 token 只由用户重新配置。
- 输出或状态变化：验证通过才替换有效文件；下载、验证与提交结果可诊断。
- 边界与失败行为：证书、HTTP 状态、内容、超时或取消失败时保留有效文件，日志不得泄露令牌。各类型下载的验证方案及 Android 代理/信任配置见 Q-007。

### R-009：仅保留模块内建定时任务

- 参与者或触发方：管理进程的订阅和 Geo 更新调度。
- 前置条件与输入：新配置启用的内建任务与调度参数。
- 必须满足的行为：由 Rust 管理器接管模块内建更新调度；旧 [crontab.cfg](../../box/crontab.cfg) 仅作 root-only 备份保留到显式完整清除，不再执行任意 root Shell 行。新调度默认沿用当前有效产品默认：旧总调度开关关闭，因此周期任务默认不运行；用户可显式启用内建计划。
- 输出或状态变化：任务类型受模块实现约束，不开放任意 Shell 命令执行面。
- 边界与失败行为：不因破坏性切换而暗中继续加载旧任务；睡眠期间错过任务的补跑和计时策略需设计，见 Q-008。

### R-010：停止/禁用优先于更新完成

- 参与者或触发方：用户停止、Root 模块禁用与后台维护任务。
- 前置条件与输入：更新可能处于下载、验证或文件提交阶段。
- 必须满足的行为：停止/禁用优先；取消未完成下载。若已进入不可分割的文件提交步骤，完成或回滚到有效文件，但不得由更新完成重新启动服务。
- 输出或状态变化：服务保持停止/禁用意图；取消与失败可以区分；文件不处于半写入状态。
- 边界与失败行为：迟到的下载结果或重试不能覆盖较新的停止/禁用意图；不可把慢下载纳入长时间阻塞停止命令的关键区。

### R-011：常驻管理进程有界恢复

- 参与者或触发方：管理进程意外退出及监督机制。
- 前置条件与输入：可识别退出原因和最近的重启记录。
- 必须满足的行为：有限次数退避重启；重启后检查并协调服务、规则和部分应用状态。多次失败后停止自动尝试、记录错误并等待人工处理。
- 输出或状态变化：可观察恢复中或需要人工处理，不永久静默失去控制，也不无限重启。
- 边界与失败行为：监督器不能依赖已退出的管理进程自身执行；具体监督形态、上限和协调顺序见 Q-006。

### R-012：内部逐单元试点，完整运行路径整体切换

- 参与者或触发方：开发、CI 与发布流程。
- 前置条件与输入：新的 Rust 运行代码及同步更新的调用方。
- 必须满足的行为：首个 arm64 单元为 `settings.json` 的 get/apply 语义、schema 契约校验（含与 2.0.0 手写校验的差异）与配置子系统的内部验证，不保留旧命令、不导入旧 Shell 设置；现有 `settings.json` 按 D-019 备份后重置，token 按 D-022 备份后清除。逐单元开发、测试和交叉编译可推进后续单元；全部运行路径完成前不发布半迁移模块。
- 输出或状态变化：正式切换需包括 WebUI、任务、安装衔接和文档/测试更新；不依靠生产兼容桥让旧脚本继续工作。
- 边界与失败行为：配置试点只验证 `settings.json`、schema 契约与差异校验、序列化和迁移；不引入 TOML、不重新引入旧 Shell 设置导入器。架构范围决定前不发布为通用替代，见 Q-001。

### R-013：分层风险验收与真实设备门禁

- 参与者或触发方：主机测试、Android 构建和设备验收。
- 前置条件与输入：可替换命令执行器、行为夹具和目标设备。
- 必须满足的行为：主机覆盖六种模式、IPv4/IPv6、启用/重建/清理和能力降级；Android arm64 交叉编译验证目标构建；设备按风险覆盖各模式族的启动、实际生效与清理，以及主要核心配置路径。产品最低系统为 Android 7.0 / API 24；支持 Magisk、KernelSU 和 APatch 的发版时当前稳定版，具体设备组合须验收。完整 Root 管理器 + API 24 矩阵是正式发布门禁；当前 API 31 / Magisk 设备可先做内部试点，正式切换前补齐（D-021）。其他 CPU 架构待 arm64 试点后再决定。
- 输出或状态变化：对已验证和未验证组合分别记录证据；正式切换/发布前必须有真实设备冒烟/整体验收。
- 边界与失败行为：编译成功不代表内核能力验证、低功耗或设备验收通过；未验证组合不能直接宣称支持。Android 7.0/API 24 与发版时当前稳定版 Root 管理器的兼容组合必须实际验证；若三家当前稳定版的版本下限使 Android 7 目标无法兑现，应在改变最低版本承诺前重新由用户确认。eBPF 作为可选能力，在未验证的 API/内核上按 R-007 降级，不宣称 API 24 上 eBPF 可用；当前 `boxbpf` 构建目标为 API 35，重建/验证为后续项，不阻塞基础支持（D-020）。主机不得直接执行会修改宿主网络或 Root 状态的模块脚本。

### R-014：升级数据与运行态处置

- 参与者或触发方：升级安装器和升级后的管理进程。
- 前置条件与输入：旧安装中的核心配置、订阅/provider/规则集、代理核心二进制、独立应用/UID 名单以及旧运行目录。
- 必须满足的行为：保留核心源配置、订阅清单、provider 文件和规则集；使用前校验，不支持或无效的文件原样保留、停用并明确报错。保留已有代理核心二进制，在启动前验证目标架构、可执行性与版本适用性；不因升级模块自动换成最新核心，不适用则拒绝启动并说明原因。`settings.json` 按 R-003/D-019 做 root-only 备份后重置为 2.0.0 默认值并将 `boot_auto_start` 置为 `false`，`githubtoken` 按 R-003/D-022 备份后清除；它们不纳入“原样保留”的用户数据范围。升级时重置并丢弃旧 [ap.list.cfg](<../../box/ap.list.cfg>)、[package.list.cfg](<../../box/package.list.cfg>)、[gid.list.cfg](<../../box/gid.list.cfg>)，不导入、不另作名单备份。归档旧日志并限制为 root-only；旧 PID、锁、能力缓存、事件状态和生成运行配置不恢复，由新管理器重建。2.0.0 已移除 sing-box；不再迁移或恢复其配置/二进制。
- 输出或状态变化：旧设置与 cron 备份按 R-003/R-009 保留；名单回到新初值，按应用/UID 分流选择需重新配置。新核心和规则的实际状态须重新观察，不继承旧状态文件的结论。
- 边界与失败行为：数据保留不等于承诺所有旧核心版本/格式可运行；名单重置是明确的数据丢弃例外，不扩大到其他核心源数据。归档旧日志可能已有敏感内容，root-only 并不等于已经完成历史日志脱敏。升级数据处置由 AC-015 验证；具体退场顺序在 Q-006 技术设计中明确。

### R-015：普通卸载与显式完整清除

- 参与者或触发方：用户发起的模块卸载或完整清除操作。
- 前置条件与输入：本模块管理的进程、任务、规则、持久数据及明确的操作请求。
- 必须满足的行为：普通卸载先停止代理核心、取消维护任务并清理本模块拥有的网络状态，再结束管理角色、移除模块程序和启动钩子，清理 PID、锁、能力缓存等瞬时运行态。保留全部持久数据，包括 `settings.json`、独立凭据、核心源配置、订阅/provider/规则集、新版本使用的名单、已有核心二进制和受保护的日志/备份；含秘密的文件保持 root-only，新日志必须脱敏。显式完整清除在列明内容并二次确认后删除 Box 数据目录内全部数据，包括 settings.json、token 及其备份、订阅、核心二进制及日志/备份；不触碰其他应用或模块的数据。
- 输出或状态变化：普通卸载后数据仍可供重装校验使用；完整清除不提供程序内恢复保证。强制卸载仍保留持久数据，不隐含完整清除。
- 边界与失败行为：停止或清理失败时默认中止卸载并保留清理入口；用户明确确认风险后才可强制继续，必须报告已知残留及手工恢复指引，不把尽力清理报告为已清干净。三家 Root 管理器是否允许原生卸载钩子中止移除尚须验证，不能只靠脚本返回码假定；相关实现门禁见 Q-004。路径与资源所有权须校验，完整清除不能跟随用户路径越界删除。

### R-016：保留用户功能，不保留旧执行契约

- 参与者或触发方：迁移设计、WebUI/CLI 重做和发布验收。
- 前置条件与输入：现有脚本和 WebUI 的用户可见功能清单，以及本规格已确认的破坏性变更。
- 必须满足的行为：保留 2.0.0 的现有用户功能（settings.json 设置、TypeScript WebUI、仅 mihomo 的核心管理、订阅/provider/规则/任务/日志等），允许重新设计 UI、命令与数据契约；为功能建立新入口和验收对应关系。明确例外为旧 CLI/JSON、可执行 Shell 设置/设置导入、任意用户 cron、token 部分明文 preview（安全原因改为 set-only），以及已确认的 settings.json/token 重置和旧名单处置变化。
- 输出或状态变化：功能保留与旧接口兼容分别可核对；升级说明列明 settings.json/token 重置、默认值变化、确认门槛和数据丢弃范围。
- 边界与失败行为：不能以“破坏性更新”为由静默删除其他用户功能；尚未完成的功能不算已迁移，也不能作为半迁移正式版本发布。

### D-001：可靠性优先的 Rust 主控制器

- 状态：已确认
- 结论：Rust 承担主要业务流程，Shell 仅保留必要平台入口；可靠性和可维护性优先。
- 理由：用户最初目标及访谈 Q1–Q3 的选择。
- 考虑过的备选：Rust 只优化少量热点，或继续以 Shell 编排为主。
- 未采用原因：不满足主要逻辑迁入 Rust 的目标。
- 影响范围：R-001、R-002、R-013。

### D-002：以破坏性切换取代兼容迁移

- 状态：已确认
- 结论：废除旧 CLI/JSON 适配、旧设置导入和长期 Shell 快照方案，受影响调用方一起更新；新 CLI/JSON 契约由 Q-009 设计（已由 D-023 确定），WebUI/测试同步更新。
- 理由：用户在访谈 Q16 的补充中明确提出直接破坏性更新，不再为兼容妥协。
- 考虑过的备选：旧接口适配、旧设置合并、TOML 生成 Shell 快照。
- 未采用原因：这些早期选择已被新要求替代，不再是当前约束。
- 影响范围：R-003、R-012、Q-009、D-023；替代关系见本节末尾。现行 `module-settings-json.md` 若要求保留旧 `{ok,data,error}` 包络，以本决定为准并在实施时同步更新该规格；现行 `module-webui-refactor.md` R-016 的 CLI 文本兼容仅适用于 2.0.0 shell，Rust `boxctl` 切换后不承诺旧文本参数/输出，实施时同步更新该规格。D-023 的 v2 契约沿用顶层键名，但不是旧命令/字段兼容。

### D-003：升级首次启动保护与默认值基线

- 状态：已确认
- 结论：新安装与升级后代理核心均默认不自启，其他默认沿用当前产品的内建值；升级后首次手动/自动启动核心前必须由用户检查并确认新配置；全新安装不额外要求迁移确认。daemon 仍随系统启动。本决定只保留首次启动保护与默认值基线；设置源见 D-018，数据重置见 D-019/D-022。
- 理由：访谈 Q9、Q17、Q20、Q40、Q43、Q58、Q59；避免重配前改变网络行为，同时不无意改变其他产品默认值。
- 考虑过的备选：一次性导入；直接沿用旧自启默认；其他项目全部保守关闭；首次逐项引导；仅靠配置有效性校验允许升级后启动。
- 未采用原因：用户选择不迁移旧值、沿用其余默认，并将升级后的显式检查与启动权限分开。
- 影响范围：R-001、R-003、R-009、D-018、D-019、D-022、AC-003、AC-016；原 Q-003 已解决。

### D-004：单二进制、常驻管理与本地 IPC

- 状态：已确认
- 结论：一个 `boxctl` 提供管理进程与轻量 CLI，经 Unix socket 协调，不新增 HTTP 管理服务。管理 daemon 随系统启动；`boot_auto_start` 只控制代理核心是否自启。
- 理由：访谈 Q23、Q26、Q59；用户选择常驻模式并明确 daemon 自启与核心自启开关分离。此前讨论的待机耗电为估算，不能声称常驻已实测更省电。
- 考虑过的备选：多个二进制；按需 CLI 加跨进程锁并保留外部监听/调度。
- 未采用原因：分别增加版本同步或跨进程状态协调复杂度；不能据此声称常驻模式已实测更省电。
- 影响范围：R-001、R-011、Q-008、Q-009。

- 未采用原因：旧 CLI 兼容与 D-002 冲突；HTTP 扩大攻击面；另造包络无收益；绕过 daemon 破坏单一协调者。
- 影响范围：R-001、R-005、R-008、R-015、R-016、Q-009、AC-020；实施时更新 `module-webui-refactor.md` 的 v1 包络/命令表、CLI 文本兼容结论和 WebUI 测试；保留 `module-webui-performance.md` 的 `ksu.spawn` 异步执行约束，不退回同步 `exec`。

### D-024：应用事务、健康检查与监督

- 状态：委托范围内决定
- 结论：每个运行变更以持久化事务日志串行执行：准备/校验 → 暂存候选 → 受控切换 → 健康检查 → 提交或回滚；失败保留 `last_good`，双失败进入人工处理；daemon 以有限退避监督核心，不用死进程的内存状态自复活。具体见第 8 节。
- 理由：跨文件、进程和内核规则不能假定原子；需要可恢复记录和明确健康判据，避免把“命令返回 0”或“PID 存在”当作成功。
- 考虑过的备选：原地编辑并直接重启；不写事务日志；用 shell 监督器；失败无限重试。
- 未采用原因：分别不可恢复、无法解释半完成状态、监督职责分散、故障循环。
- 影响范围：R-005、R-006、R-007、R-011、R-014、R-015、Q-006、AC-021；实施时按第 8 节落地。`module-service-start-restart-ordering.md`/`module-service-stop-cleanup.md` 的“不增加 watchdog”是 2.0.0 局部范围，Rust 切换时由本决定的 `boxctld` 监督扩展，需同步更新这两份规格。

### D-025：下载信任、代理边界与内容验证

- 状态：委托范围内决定
- 结论：下载只用受信任 TLS；默认 Android 系统 CA 目录，不可用时使用随包 Mozilla 根证书作受控回退；独立 daemon 不使用需要 JVM 的 platform-verifier，不提供 insecure、明文 HTTP 或 curl/wget 回退。默认直连、不隐式读取系统代理；保留现有 `use_ghproxy`/`url_ghproxy` 作为显式 GitHub 公共下载镜像（仅 GitHub 主机、https、不发送 token、失败不自动回退），不新增其他代理/PAC。token 只发 GitHub 允许的 hosts，跨 host 重定向剥离 Authorization；下载内容限大小并按格式、架构、版本及可用的 SHA256 校验，不执行下载内容。TLS 根/API24/镜像/资产验证未执行。
- 理由：当前 shell 下载使用 `--insecure`/`--no-check-certificate`，不能带入 Rust；Rust 原生 HTTP 已有 host/API24 依赖冒烟，但 Android 信任根和内容验证仍需设备证据。
- 考虑过的备选：保留 curl/wget 回退；关闭证书校验；隐式使用系统代理；把 token 跟随所有重定向；只校验 HTTP 状态不校验内容。
- 未采用原因：分别破坏 TLS 默认、扩大凭据暴露、行为不可解释、接受无效/错误架构资产。
- 影响范围：R-008、Q-007、AC-022；实施时补充 TLS 根来源、代理和资产验证记录。

### D-026：网络事件、调度边界与功耗验证

- 状态：委托范围内决定
- 结论：daemon 以事件驱动为主，监听链路/地址变化并查询 Wi-Fi SSID/BSSID；查询不可用时按未知处理并有限重试，不把未知当断开。事件 2–3s 稳定窗口去抖、相同状态去重，无事件源/唤醒后用 30s 兜底轮询。内建订阅/Geo 定时任务由 daemon 计时，默认关闭；睡眠/停机后错过任务在宽限期内最多补一次；停止/禁用优先。功耗不宣称常驻更省电，须同设备/配置/流量实测。API24/功耗验证未执行。
- 理由：当前 `net.inotify` 由 `inotifyd` 监控 `/data/misc/net` 的写事件，使用 3s 冷却窗口和 `last_check_time`/`last_wifi_state` 状态文件；`cmd wifi` 主要读取 SSID/BSSID，Wi-Fi 连通性由 `ctr.utils` 的默认路由接口判断，没有 `dumpsys wifi` 回退。Rust 应统一事件输入、去重和停止优先，并保留未知状态的安全默认；不能把当前 shell 的 inotifyd/冷却机制误写成 netlink 稳定窗口。
- 考虑过的备选：高频轮询；把未知 Wi-Fi 当断开；保留任意 cron；睡眠后补跑全部错过任务；宣称常驻天然省电。
- 未采用原因：分别增加功耗/抖动、误停服务、扩大执行面、补跑风暴、无实测依据。
- 影响范围：R-001、R-004、R-009、Q-008、AC-023；实施时补 API24/API31 和功耗测量。

### D-027：移除 eBPF 支持（2026-11-26）

- 状态：用户明确要求
- 结论：删除 eBPF 网络模式、`cnip_mode=ebpf`、`boxbpf` 探测/二进制和相关规则发布预留代码；网络模式只保留 TUN、TProxy、Redirect、Mixed、Enhance，CNIP 只保留 ipset。
- 迁移：旧 settings.json 中的 `network_mode=ebpf` 自动迁移为 `tproxy`，`cnip_mode=ebpf` 自动迁移为 `ipset`，避免升级后 daemon 因旧值无法加载。
- 范围：`box/bin/boxbpf`、`customize.sh` 权限处理、WebUI 选项、settings schema、Rust capabilities/service/network/task 路径一并删除。
- 理由：用户当前设备没有 eBPF 核心，且明确要求不再保留该能力；保留未实现的分支只会制造“可用”的假象。

### 当前实现范围补充（final51）

- eBPF 相关网络模式、CNIP 模式、`boxbpf` 探测/二进制、WebUI 选项、schema 与 Rust 分支均已移除；
- 旧 `network_mode=ebpf` 迁移为 `tproxy`，旧 `cnip_mode=ebpf` 迁移为 `ipset`；
- 聚合订阅常见 `proxies: [] + proxy-providers` 已接受；规则模板应用时合并已有 rule-providers，避免 DNS `rule-set` 引用丢失；
- Rust 108 unit + 27 integration = 135；WebUI 39；
- final53 已安装 KSU；WebUI 逐项点击验证概览启停/重启/重载、订阅更新、规则订阅下载/应用/重载、设置保存、核心配置保存、任务与日志；订阅更新任务已从“已中断”修复为“已完成”，节点 API 加载 99 个节点。

## 8. 技术设计

### 默认值基线

`settings.json` 采用 2.0.0 当前产品的内建默认行为；现有用户 `settings.json` 按 D-019 做 root-only 备份后重置为默认值，不导入旧值。2.0.0 的 `box/settings.json` 与 `box/settings.default.json` 当前内容相同；实现必须校验两者与 schema 一致，重置以安装的 `settings.default.json` 为基线并强制 `boot_auto_start=false`，不能因两文件漂移静默选一个。就默认值本身而言，代理核心开机自启是相对 2.0.0 默认的唯一变更，改为关闭（`boot_auto_start=false`）；用户设置重置属于数据处置，见 D-019。当前默认基线见 [settings.default.json](../../box/settings.default.json) 与 [settings.schema.json](../../box/settings.schema.json)：核心 mihomo、TUN、IPv6 开启、Wi-Fi 自动控制关闭、CNIP 绕过关闭、核心代理模式。订阅更新开关虽为开启，但周期总调度开关 `run_crontab=false`，因此新版本周期任务默认不执行，除非用户显式配置调度。Rust 以 schema 为目标契约并显式实现校验；当前运行期并未读取 schema，不能把“文件存在”当作“校验已存在”。如需新增字段，必须更新 schema/default 并建立“旧内建默认 → 新语义”清单，不能从示例推断未列字段或恢复用户自定义值。

### 已确认的职责与主要交互

```text
必要的 Root/Shell 入口 ──> boxctl 管理进程
                              ↑
WebUI ──> boxctl CLI ── 本地 Unix socket
                              │
网络事件/内建调度 ────────────┤
                              ↓
                        统一状态协调者
                 ┌────────────┼─────────────┐
                 ↓            ↓             ↓
              配置/版本     服务/规则      维护/下载
                 │            │             │
           候选运行配置    代理核心及工具    Rust HTTP
```

| 程序内职责 | 负责内容 | 边界 |
|---|---|---|
| 配置 | settings.json、源配置、候选及生效版本 | 不执行旧 Shell 设置，不引入 TOML，不把所有核心格式强塞进同一文件 |
| 服务运行 | 核心生命周期、健康与进程状态 | 不在启动时污染用户源配置 |
| 网络策略 | 能力、规则计划、批量应用与清理 | 调用现有工具，不首版重造内核接口 |
| 网络事件 | 观察网络和模块开关、去重、策略输入 | 只提交事件，不绕过协调者改规则 |
| 维护更新 | 订阅/Geo/核心维护、HTTP、验证与提交 | 不执行任意用户 cron，不覆盖停止意图 |
| 状态协调 | 控制方式、目标/实际状态、应用确认、优先级与恢复 | 同一关键状态变更只有统一所有者 |

这些是单二进制内的模块，不是微服务；具体 crate 或目录布局尚未定稿。

### Rust 工作区与模块边界

**建议布局**（单二进制约束来自 D-004；具体 crate 拆分可在实现时调整，依赖方向不得反转）：

```text
rust/
  Cargo.toml                 # workspace（可选；也可先用单 crate）
  crates/
    boxctl/                  # bin: CLI + daemon 入口
    boxctl-core/             # 状态机、设置、配置、任务、事务
    boxctl-platform/          # Android/Root/命令/路径/权限适配
    boxctl-http/              # TLS 下载、镜像、内容验证
    boxctl-protocol/          # v2 包络、NDJSON、错误码
    boxctl-testkit/           # fake runner/clock/socket/TLS
```

| 模块 | 职责 | 依赖 | 不负责 |
|---|---|---|---|
| `cli` | 解析人类命令行、映射到协议、文本/JSON 输出 | `protocol` | 业务状态变更 |
| `protocol` | v2 包络、NDJSON 帧、错误码、版本/退出码映射 | 无业务依赖 | 直接操作文件 |
| `daemon` | Unix socket、请求分发、生命周期、监督 | `protocol`、`state`、`service` | 具体网络规则算法 |
| `state` | revision、事务日志、锁、恢复、`last_good` 指针 | `platform` | 用户配置语义 |
| `settings` | schema 校验、settings/token 原子读写、备份/重置 | `state`、`platform` | 核心 YAML 运行配置 |
| `config` | mihomo YAML 读取/结构化校验/候选生成 | `settings`、`platform` | 核心进程生命周期 |
| `service` | 核心进程、健康检查、启动/停止/重启事务 | `state`、`config`、`network` | HTTP 下载 |
| `network` | 能力探测、iptables/ipset/eBPF/TUN 规则计划与清理 | `platform` | 订阅/任务调度 |
| `events` | netlink/Wi-Fi/模块开关事件、去抖、调度器 | `state`、`service` | 直接改规则 |
| `download` | TLS/镜像/认证/内容验证/原子提交 | `platform` | 服务状态决策 |
| `tasks` | 任务目录、状态、日志、取消、保留策略 | `state`、`service` | 业务重试策略 |
| `platform` | Android/Root 命令、路径、权限、PID 身份 | 无 | 业务规则 |
| `testkit` | fake runner/clock/TLS/socket、fixture | 仅测试 feature | 生产逻辑 |

- 依赖方向：`cli → protocol`；`daemon → protocol/state/service/network/events/download/tasks/settings/config/platform`；`platform` 不依赖业务模块；禁止反向依赖和循环依赖。
- crate 拆分不是产品承诺；首单元允许先单 crate 模块化，再按编译/测试边界拆分。
- 构建目标：`aarch64-linux-android24`；Rust 1.98.1、NDK 29；产物安装为 `/data/adb/box/bin/boxctl`；`box_service.sh` 只启动 `boxctl daemon`。

### CLI、JSON 与 Unix socket 契约（Q-009）

**角色与传输**

- 同一个 `boxctl` 二进制：用户/脚本调用 CLI；`box_service.sh` 以 `boxctl daemon` 启动常驻管理进程。CLI 不自动拉起第二个 daemon；daemon 不可用时按本节降级/报错。
- 控制面只有 `/data/adb/box/run/boxctl/control.sock`（Unix stream）。`run/boxctl/` 目录 0700，socket 0600，root:root；daemon 通过 `SO_PEERCRED` 校验 UID 0。不新增 TCP/HTTP/端口/网络监听。
- 每个连接按 NDJSON 处理一条请求和一条响应；单条上限 1 MiB；请求带 `id`，响应回显。连接断开不取消已接受的长任务；取消必须显式 `task.cancel`。
- 变更只能经 daemon：CLI 不直接写 `settings.json`、核心配置、规则或任务目录；只读离线检查例外见“daemon 不可用”。

**v2 包络**

```json
{"ok":true,"data":{},"meta":{"version":2,"protocol":1,"request_id":"...","duration_ms":12,"revision":42,"warnings":[]}}
{"ok":false,"error":{"code":"E_VALIDATION","message":"...","detail":"...","retryable":false},"meta":{"version":2,"protocol":1,"request_id":"..."}}
```

- `meta.version=2` 是 JSON 契约版本；`protocol=1` 是 socket 协议版本；两者独立。`request_id` 回显；`revision` 在状态变更后递增；`warnings` 用于可选能力降级，元素为 `{code,message}`，不把成功改成失败。
- `--json` 模式 stdout 只输出包络；日志/诊断写 stderr；不把 token、完整订阅 URL、规则内容等敏感值写入日志。
- 顶层键名靠近 2.0.0 的 `{ok,data,error,meta}` 是为复用 WebUI 解析器；这是新 v2 契约，不保证旧 `box.tool --json` 命令、参数位置或字段语义。

**方法与 CLI 映射**

| 能力 | CLI（全局 `--json` 可选） | socket method | 主要 data |
|---|---|---|---|
| 状态/诊断 | `boxctl status`、`boxctl doctor`、`boxctl version` | `status.get`、`doctor.check`、`version.get` | daemon、revision、upgrade、capabilities、warnings |
| 服务 | `service start/stop/restart/reload` | `service.*` | action、output、status |
| 设置 | `settings get/apply/set` | `settings.get`、`settings.apply`、`settings.set` | settings 扁平 map、sensitive、changed[] |
| 配置 | `config get/apply/delete` | `config.get`、`config.apply`、`config.delete` | proxy-groups、rule-providers、rules、changed[] |
| 核心 | `core get/apply` | `core.get`、`core.apply` | core、file、structured、raw |
| 名单 | `lists get/apply` | `lists.get`、`lists.apply` | package、gid、interfaces、files |
| 规则集 | `rule-profile ...` | `rule_profile.*` | 与 2.0.0 的 `RuleProfile*` 数据形状一致 |
| 订阅 | `sub list/get/add/set/rm/enable/disable/update` | `sub.*` | 与 2.0.0 的 `Subscription*` 数据形状一致 |
| 任务 | `task start/status/logs/list/cancel` | `task.*` | id、kind、state、cancelable、exit_code、lines |
| 日志/重置 | `logs get/clear`、`reset subscriptions` | `logs.*`、`reset.subscriptions` | file、lines、cleared |
| 升级确认 | `upgrade status/confirm` | `upgrade.status`、`upgrade.confirm` | required、confirmed、from/to |
| 卸载/清除 | `uninstall preflight/apply/force`、`purge plan/apply` | `uninstall.*`、`purge.*` | blockers、report、token、expires_at |
| 旧维护 | `internal <action>` | `internal.*` | 不承诺兼容；仅供未迁完的 Shell 入口 |

- `settings apply`/`config apply` 接受文件路径或 `--stdin`；daemon 读取并校验，不把 JSON 拼进 shell 命令。
- 全局 `--json` 放在任意位置都生效；`--socket <path>` 用于测试；`--timeout <duration>` 只控制客户端等待，不取消已接受的服务端操作。
- 旧的 `upkernel`/`upkernels`/`upgeox_all`/`upxui`/`upcnip` 等维护入口优先映射为 `task.start` 的白名单 kind；`subs`、`geox`、`geosub` 映射为 `task.start` 的 `sub-update`/`geox`（`geosub` 为两步按序，不新增 shell 别名）；`reload` 映射为 `service reload`；`check` 映射为 `doctor.check`；`webroot`、`memcg`、`blkio`、`bond0`、`bond1`、`upyq`、`upcurl`、`all` 等暂收进 `internal`，逐个迁入，不作为公开契约；`taskset_cpu`/`cgroup_*` 由服务资源限制应用，不是 CLI 命令。
- 旧 `box.tool`（文本和 `--json`）不提供适配层；WebUI、测试、Shell 入口统一改调 `boxctl`，旧命令调用返回 `E_USAGE`/不存在，而不是静默转发。

**CLI 退出码**

| 退出码 | 含义 | 典型错误码 |
|---|---|---|
| 0 | 成功（含可选能力降级警告） | — |
| 1 | 内部/未分类 | `E_INTERNAL` |
| 2 | 用法/参数 | `E_USAGE` |
| 3 | 校验/数据无效 | `E_VALIDATION` |
| 4 | 权限/非 root | `E_PERMISSION` |
| 5 | daemon/socket 不可用 | `E_MANAGER_UNAVAILABLE`、`E_PROTOCOL` |
| 6 | 冲突/忙/版本不匹配 | `E_CONFLICT`、`E_BUSY`、`E_VERSION_MISMATCH` |
| 7 | 需要显式确认 | `E_NEEDS_CONFIRMATION` |
| 8 | 未找到 | `E_NOT_FOUND` |
| 9 | 超时 | `E_TIMEOUT` |
| 10 | 已取消 | `E_CANCELED`、`E_INTERRUPTED` |

- `--json` 失败仍返回包络并给非零退出码；成功有 `warnings` 仍为 0。WebUI 以 `ok` 和 `error.code` 为准，不解析人类文本。
- 2.0.0 实际 `json_error` 集合为 `E_BUSY`/`E_COMMAND`/`E_CONFLICT`/`E_DOWNLOAD`/`E_INTERRUPTED`/`E_IO`/`E_NOT_FOUND`/`E_RELOAD`/`E_USAGE`/`E_VALIDATION`；`E_DOWNLOAD`/`E_RELOAD` 已存在，不是 v2 新增，且 2.0.0 没有 `E_CANCELED`（取消成功放在 `data.state=canceled`）。v2 保留上述集合并新增 `E_CANCELED`、`E_MANAGER_UNAVAILABLE`、`E_PROTOCOL`、`E_VERSION_MISMATCH`、`E_PERMISSION`、`E_TIMEOUT`、`E_NEEDS_CONFIRMATION`、`E_INTERNAL`、`E_TLS`、`E_CONTENT`、`E_ARCH`、`E_CHECKSUM`；不新增 `E_DEGRADED`，可选降级用 `warnings`。

**版本、并发与幂等**

- CLI 在请求中带 `client_version` 和 `protocol=1`；daemon 返回 `server_version`。协议不匹配返回 `E_PROTOCOL`；契约主版本不匹配返回 `E_VERSION_MISMATCH`；补丁/次版本差异只告警，不静默接受未知字段。
- 每次状态变更返回递增的 `meta.revision`；`settings.apply`/`config.apply`/`settings.set` 可带 `if_revision`，不匹配返回 `E_CONFLICT`，避免 WebUI 旧页面覆盖新状态；不带 `if_revision` 时按“无前置条件”处理，CLI 脚本应显式带。
- 读请求可并发；变更由 daemon 串行。长任务沿用 2.0.0 的单任务语义：同一时间只允许一个变更任务，普通冲突返回 `E_BUSY`；`upkernel` 不可取消，其余可 `task.cancel`；stop/disable 是优先级更高的例外，先取消可取消任务、把不可取消任务标记 interrupted，再进入停止事务，不因 E_BUSY 拒绝；任务完成后最多保留 20 个目录。
- `upgrade.confirm` 幂等；无待确认项时返回当前状态而非重复写入。`purge.plan` 生成一次性 token，root-only、短 TTL（建议 5 分钟）；`purge.apply` 必须同时带有效 token 和 `confirm=true`，过期/复用返回 `E_CONFLICT`。
- 请求的 `request_id` 用于日志关联；不承诺跨请求去重。客户端超时/断连不撤销已接受的服务端变更；需要撤销时用 `task.cancel` 或显式停止。

**daemon 不可用、升级与卸载**

- `status`、`version`、`doctor` 可在 daemon 不可用时工作：返回 `data.daemon=false`、`degraded=true` 和 warnings；不伪造运行状态。其余命令返回 `E_MANAGER_UNAVAILABLE`；CLI 不自动启动第二个 daemon，由 `box_service.sh`/Root 服务管理器启动。
- `status` 包含 `upgrade.required`/`confirmed`；升级后未确认时，显式/自动核心启动返回 `E_NEEDS_CONFIRMATION`，daemon 仍允许 `settings get`/`config get` 检查。`upgrade.confirm` 只由 root 调用；不提供“跳过确认”的 CLI 参数。
- `uninstall.preflight` 返回阻塞项/是否可强制；`uninstall.apply` 执行普通清理，阻塞时返回 `E_CONFLICT` 且不删除持久数据；`uninstall.force` 仅在 preflight 允许时接受 `confirm=true`，返回残留风险。`purge.plan`/`purge.apply` 只允许删除 `/data/adb/box` 内由本模块拥有的数据，路径必须规范化且在白名单内；不跟随 symlink，不清空其他目录。
- 2.0.0 当前 `uninstall.sh` 直接 `rm -rf /data/adb/box`，与本契约和 R-015 冲突；Q-004 必须重写为“默认中止/显式强制/完整清除”的平台入口，本文只定义 CLI 交互，不把当前脚本当目标实现。
- Root 管理器可能在脚本之外强制移除模块；`uninstall.force` 的清理入口不能替代平台层验证，该限制仍由 R-015/Q-004 跟踪。

**安全与数据**

- socket 仅 root；daemon 用 peer credentials 复核 UID 0；拒绝非 root、超大消息、非法 JSON、未知 method、路径穿越和 symbolic-link 目标。无网络监听，不接受远程地址。
- 不执行任意命令：`task.start` 只接受白名单 kind 和结构化参数；维护命令走 `internal` 白名单；不把用户字符串传给 `sh -c`。
- 临时文件 0600、原子替换；`settings.get` 只返回 `sensitive.githubtoken.set`，不返回 preview/部分明文；`sub.get` 才返回完整 URL 用于编辑；日志脱敏；错误 detail 不回传 token/完整 URL。
- `settings.json`/`githubtoken` 的备份、重置、清除仍按 D-019/D-022；v2 契约不改变升级数据语义。

**WebUI 与测试更新**

### 接口字段与错误契约

**通用 v2 包络**

| 字段路径 | 类型 | 必填/出现条件 | 可为 null | 默认行为 | 含义与约束 |

### 应用事务、健康检查与监督（Q-006）

**事务单元与状态**

- 事务单元：start、stop、restart、apply settings、apply config、mode switch、core update task；卸载清理按 Q-004/R-015 复用同一日志，但删除范围不由此处扩大。
- 同一时间只允许一个运行变更事务；读请求/状态查询可并发；普通第二变更返回 `E_BUSY`；stop/disable 例外，先取消可取消任务、把不可取消任务标记 interrupted，再进入停止事务，不被 E_BUSY 拒绝。事务由 daemon 持有，CLI/WebUI 只提交请求和查询。
- 每次事务分配 `txid`，在 daemon 专用持久目录 `state/tx/<txid>/` 保存 `manifest.json`（修订、来源、前后哈希、候选路径）和 `state.json`（阶段、时间、错误、PID 身份）；原子写入并 fsync，目录 0700、文件 0600。不得把事务状态放在启动时会清理的临时 `run/`；具体落盘由 Q-004 统一。
- 阶段：`preparing` → `staged` → `switching` → `verifying` → `applied`；失败进入 `rolling_back`，回滚成功回到 `applied`（旧版本）或 `stopped`，双失败进入 `manual`；取消进入 `canceled`。状态跨 daemon/设备重启保留。

**切换顺序与失败边界**

| 操作 | 顺序 | 失败处理 |
|---|---|---|
| 从停止启动 | 校验 → 启动候选核心 → 等待 ready → 应用必需规则 → 健康检查 → 提交 | 任一步失败：停止候选核心、清理本次规则、保持停止；不把半启动当成功 |
| 运行中 restart/应用设置或配置 | 校验 → 暂存候选 → 移除本模块规则 → 停止旧核心 → 启动候选 → ready → 应用规则 → 健康检查 → 提交 | 规则移除失败：保留旧核心并中止；后续失败：恢复 last_good 核心与规则；回滚失败进入 manual |
| stop/disable | 取消可取消任务，不可取消任务标记 interrupted → 移除本模块规则 → 停止核心 → 清理瞬时状态 | 规则移除失败：保留核心并报错（与当前 service stop 一致）；停止失败：有限强制停止，仍失败进入 manual；迟到任务结果不得提交或重启核心 |
| 卸载 | 按 R-015/Q-004 先停止核心、取消任务、清理自有规则，再结束管理角色 | 清理失败默认中止；强制/完整清除按 R-015，事务只记录不扩大删除 |
| 核心更新任务 | 校验候选二进制/架构 → 暂存 → 同 restart 事务 → 成功后再替换 last_good | 失败保留旧核心；不自动换成最新版 |

- 2.0.0 当前 `box.tool service start` 在 `box.iptables renew` 失败时返回 `E_COMMAND`，但不会停止已启动核心或清理刚应用的规则；本表“任一步失败停止候选核心/清理本次规则”是 Rust 目标，不是当前行为。
- 应用设置/配置只改源文件/运行副本，不直接改用户核心源；运行副本在 `run/candidates/<txid>/`（瞬时，重启后可重建），候选 0600，成功后才更新 `state/` 中的 `last_good` 指针；候选缺失时按未完成事务保守处理。
- `cgroup_memcg`/`taskset_cpu`/`cgroup_blkio` 等资源限制在候选核心启动后、ready/健康检查前应用；不可用/设置失败属于可选能力降级，记录 warning 并继续，不阻断核心；停止/回滚清理本模块创建的作用域，不杀其他进程，不宣称限制已生效。
- `last_good` 保留最近 2 个成功候选和 1 个失败候选，最多 5 个；清理旧候选不得删除源配置、订阅、核心二进制或备份。
- `settings.json`/token 的备份/重置/清除是独立数据步骤（D-019/D-022），不因事务回滚恢复旧 token 或旧个人设置。

**健康判据**

- 核心进程存在且 PID 身份（可执行路径/启动时间）匹配；启动后观察窗口内未立即退出；预期监听端口或 TUN 接口存在；启动日志无致命配置错误；本模块必需规则存在；配置了 external-controller 时可做只读探测。
- 默认观察窗口 5s、轮询 100ms，可配置；不以单次 PID 存在、单条命令返回 0 或端口短暂打开作为成功。健康检查不发送真实用户流量，不宣称网络已通/已断、fail-closed 或 kill switch。
- 健康检查失败按上表回滚；回滚后再次健康检查，旧版本仍不健康则进入 manual，不无限重试。

**取消、停止优先与崩溃恢复**

- `task.cancel` 只在安全点生效：切换前可干净取消；停止旧核心后、提交前取消则走回滚；提交后取消返回 `E_CONFLICT` 并说明已完成。异步取消不 `kill -9` 正在原子写入的进程。
- stop/disable 先持久化停止意图，再取消任务；D-008 的停止优先不变；事务不得因迟到任务结果重新启用核心。
- daemon 启动时读取未完成事务：`preparing/staged` 丢弃候选；`switching/verifying` 先核对实际进程/规则，健康则提交，否则回滚；`rolling_back` 继续或完成回滚；`applied` 重新核对健康，不健康则回滚到 `last_good`；候选缺失或无法判定进入 manual；`manual` 不自动重试，只能由用户显式 start/apply 重新进入校验。
- PID 文件只是线索；用进程身份/启动时间/锁校验，避免杀掉同名其他进程；跨文件、进程和内核操作按阶段记录，不声称整体原子。

**状态机与故障矩阵**

| 状态 | 含义 | 允许转移 | 持久化内容 |
|---|---|---|---|
| `idle` | 无运行事务 | `preparing` | 无 |
| `preparing` | 校验源/候选/能力 | `staged`、`canceled`、`manual` | txid、来源、错误 |
| `staged` | 候选已落盘，未改运行态 | `switching`、`canceled` | 候选路径/哈希 |
| `switching` | 停旧/启新/应用规则 | `verifying`、`rolling_back`、`manual` | 步骤、PID 身份 |
| `verifying` | 健康观察 | `applied`、`rolling_back`、`manual` | 健康结果、时间 |
| `applied` | 新版本健康，已提交 | `rolling_back`（后续健康失败）、`preparing`（新事务） | revision、last_good |
| `rolling_back` | 恢复 last_good | `applied`、`stopped`、`manual` | 回滚步骤/结果 |
| `manual` | 需人工处理 | 仅显式 start/apply 重新校验 | 原因、最后错误 |
| `canceled` | 安全点取消 | 无（新事务重新开始） | 取消点 |

| 故障 | 期望动作 | 不得 |
|---|---|---|
| 校验失败 | 不改变运行态，保持健康服务；返回 E_VALIDATION | 停止健康服务/覆盖源文件 |
| 新核心启动失败 | 停止候选、清理本次规则；恢复旧核心或保持停止 | 把半启动当成功 |
| 必需规则失败 | 停止候选、回滚旧版本/规则 | 宣称完整成功或全局清空规则 |
| 健康检查失败 | 回滚 last_good；再次健康检查 | 无限重试或静默接受 |
| 回滚失败 | 停止核心、尽力清理自有资源、进入 manual | 自动循环重启/掩盖失败 |
| daemon 崩溃在 switching/verifying | 重启后核对实际状态；可判定则提交/回滚，否则 manual | 假定子进程仍健康 |
| 取消在提交前 | 回滚或安全停止 | 提交一半后返回 canceled |
| 取消在提交后 | 返回已完成/E_CONFLICT | 假装撤销已生效变更 |

**监督与退避**

- `boxctld` 是核心的监督者；核心意外退出时按 1s、2s、4s、8s、16s 退避重启，最多 5 次；连续健康 60s 后重置计数。参数可配置，默认值不是实测功耗/恢复结论。
- 用户 stop/disable、manual 状态、升级未确认时不得自动拉起核心；daemon 崩溃由 `box_service.sh`/平台服务管理器重启，daemon 不依赖已死进程的内存任务自我复活。
- `status` 暴露 `txid`、阶段、`revision`、`last_error`、`manual` 原因；日志脱敏。监督只处理核心进程，不绕过事务直接改规则。

**边界**

- 不承诺跨文件/进程/内核的原子提交；以日志、候选、健康检查和回滚保证可解释恢复。
- 不把停止核心、失败清理或回滚描述为必然断网、防直连或 fail-closed；不全局清空他人规则；不覆盖用户核心源配置。
- 事务参数/退避值可按设备实测调整，但改变“双失败停核心/人工处理”“停止优先”等已确认行为需用户确认。

### 下载信任、代理与内容验证（Q-007）

**TLS 与信任**

- 只用 rustls；证书链、主机名、有效期校验默认开启；不提供 `--insecure`、跳过校验、明文 HTTP 或 curl/wget 自动回退。
- 信任根优先 Android 系统 CA 目录（`/system/etc/security/cacerts`、conscrypt）；独立 daemon 没有 JVM，不使用 `rustls-platform-verifier`，系统根不可用时使用随包 Mozilla 根证书作为受控回退；`doctor` 显示当前来源，不静默切换。
- 证书错误、过期、主机名不符、链不完整、TLS 版本/套件失败一律失败；不把失败重试为 insecure。v1 不引入自定义 CA/pinning；未来增加需用户确认。
- 连接/读写超时和大小上限；重定向最多 5 次且只允许 http/https；跨 host 重定向剥离 Authorization；拒绝 `file://` 等其他 scheme；不把 stderr/HTML 当内容。

**代理与镜像**

- 默认直连；不隐式读取 `http_proxy`/`https_proxy`/PAC/Android 全局代理；不新增其他代理/PAC 设置。需要系统/应用代理时单独设计并确认，不在代码里静默 fallback。
- 保留 settings 中现有的 `use_ghproxy`/`url_ghproxy`：仅对 GitHub 下载 URL（`github.com`、`raw.githubusercontent.com`、`gist.github.com`、`gist.githubusercontent.com` 等允许列表）重写为 `url_ghproxy/<原 URL>`；镜像必须为 `https://`，设置校验/使用前拒绝 http 或其他 scheme，镜像请求不携带 Authorization，镜像失败不自动回退直连，报告明确错误。
- 订阅 URL 与 GitHub API 各自直连；不把 GitHub token 带到订阅 URL；镜像仅用于公开 GitHub 下载，私有资产只允许直连；不自动切换镜像。

**认证与 token**

- token 从 `/data/adb/box/githubtoken`（root-only 0600）读取；只发 `api.github.com`/`github.com`/GitHub release asset 允许列表；跨 host 重定向剥离；镜像请求不携带 token；不写入 URL query、日志、错误 detail、`settings get`。
- `settings get` 只返回 `sensitive.githubtoken.set`，不返回 preview；设置/清除 token 走 root-only CLI/WebUI；D-022 迁移备份/清除不变。2.0.0 的 preview 是待移除的旧行为。
- `subscription_user_agent` 只用于订阅/provider 下载，保留 2.0.0 默认值与设置；拒绝 CR/LF/控制字符和超长值；不用于 GitHub API/镜像，不改变 token 策略。
- GitHub 401/403/429：不无限重试；报告状态/重置时间；不降级到匿名、明文或其他 host。
- `ruleset_prefix`、`cn_ip_url`、`cn_ipv6_url` 等用户 URL 同受 TLS/重定向/大小/内容校验；不隐式套镜像，只有明确 GitHub URL 且用户开启 `use_ghproxy` 时才按镜像规则处理。

**内容验证**

- 下载最大 32 MiB（可配置上限，不超过硬上限）；流式写临时文件 0600；失败/取消删除临时文件，不覆盖有效文件。
- 按类型校验：订阅/provider 解析 YAML/JSON 并检查必要结构；核心二进制校验 ELF 架构/ABI/可执行位；Geo/规则集校验格式/非空/大小；压缩包拒绝绝对路径、`..`、symlink 逃逸；不执行下载内容。
- 有发布 SHA256 时必须校验；没有时明确“仅 TLS/GitHub 信任”，不宣称签名验证；版本/架构不匹配拒绝；原子替换仅在全部校验通过后。
- 沿用 2.0.0 的 `E_DOWNLOAD`；补充 `E_TLS`、`E_CONTENT`、`E_ARCH`、`E_CHECKSUM`、`E_TIMEOUT`、`E_CANCELED`；见 AC-022。

**验证项**

- API 24/API 31 系统信任根与回退、坏证书、跨 host 重定向、token allowlist、`use_ghproxy` 成功/失败/不携带 token/非 https 镜像拒绝、超大/无效/错误架构/校验和不符、取消、无 insecure/无隐式代理；AC-022 未执行，不能宣称已验证。

### 网络事件、调度与功耗（Q-008）

**事件源与状态**

**2.0.0 当前基线**：`start.sh` 启动 `inotifyd` 监控 `/data/misc/net`；`net.inotify` 只处理写事件，`CTRL_STABILITY_WINDOW=3` 是冷却窗口，不是等待稳定；状态文件为 `run/state/last_check_time`、`last_wifi_state`；`cmd wifi status` 主要解析 SSID/BSSID，Wi-Fi 是否连通由 `ctr.utils` 的默认路由接口判断，没有 `dumpsys wifi` 回退。以下 netlink/`ip monitor`/30s 兜底是 Rust 目标，不是当前已有实现。

- 主事件源：netlink/`ip monitor` 的链路/地址变化；Wi-Fi 状态用 `cmd wifi status`；不可用时保守解析 `dumpsys wifi`，仍不可用按 unknown；不把查询失败/空 SSID 当断开。
- 事件字段：transport（wifi/cellular/ethernet/none）、iface、ssid、bssid、validated；只提交协调者，不直接启停服务。
- 2–3s 稳定窗口；相同 `(transport,iface,ssid,bssid)` 去重；控制模式手动优先；未知保持现状并有限重试。
- 无事件源/唤醒后 30s 兜底轮询；事件正常时不高频轮询；重试有上限/退避；睡眠/唤醒重新评估，不补发历史事件。
- 停止/禁用/升级未确认优先；事件不得绕过这些门槛。

**调度**

- daemon 内建 timer；只支持订阅/Geo 等白名单任务；不执行任意 cron；默认 `run_crontab=false`；用户显式启用后按间隔执行；加 jitter 避免同时；停止/禁用取消。
- 睡眠/daemon 停机后错过任务在宽限期（建议 1h）内最多补一次；不补跑风暴；手动更新不受调度开关限制；任务状态持久化。
- 长任务沿用单任务语义；调度不覆盖停止意图；失败有限重试，达到上限等待人工/下次显式触发。

**功耗与验证**

- 事件驱动、避免高频轮询和不必要的 wake lock；常驻本身不保证省电；同设备、同配置、同流量测量 CPU/内存/唤醒/电量；不宣称数值预算或“已省电”。
- 验证 API 24/API 31 的 Wi-Fi 开关、SSID/BSSID、蜂窝/以太网、未知状态、睡眠/唤醒、调度到期/错过、停止/禁用；AC-023 未执行。

### 术语与不变量

- **控制方式**回答谁决定服务启停；**代理网络模式**回答如何接管流量，二者不可混用。
- **期望配置**是已保存内容；**生效配置**是当前有效运行版本，保存成功不能把两者自动画等号。
- **目标服务状态**来自有效控制意图；**实际服务状态**来自进程和规则观察，不能只看 PID 文件即认为正常。
- 管理器不得把迟到任务结果视为新的启动授权；停止/禁用优先规则见 D-008。
- 核心启动、文件提交和网络变更是不同步骤；恢复记录必须能够说明哪一步成功、哪一步失败。

### 控制意图、自动启动门槛与观察状态

控制模式、最后期望启停状态、代理网络模式是不同概念；Root 启用状态、核心自启开关、升级配置确认和配置有效性是启动门槛，不应通过改写持久化用户意图来实现。daemon 是否运行也不等于核心是否运行。

以下仅说明设备启动/模块重新启用时的核心恢复，不代替 daemon 崩溃后的真实状态核对：

| 条件 | 核心行为 |
|---|---|
| Root 模块禁用 | 停核心并清理自有网络状态；不允许自动启动 |
| 升级配置尚未由用户检查确认 | 首次核心手动/自动启动均阻止；daemon 仍可提供检查/配置功能 |
| 模块启用、确认门槛满足，但核心自启关闭 | 不自动拉起核心；有效的显式用户启动不受该开关禁止 |
| 核心自启开启，手动模式 | 恢复持久化期望状态：最后停止则保持停止，最后启动则校验后启动 |
| 核心自启开启，自动模式 | 重新评估当前 Wi-Fi 策略，不照搬旧事件缓存 |
| Wi-Fi 未知而非确认断开 | 保持当前实际服务状态并有限重试；在启动时尚未运行则继续保持停止 |
| 已进入需人工处理状态 | 网络事件或监督器不得绕过故障状态无限自动重试 |

显式用户 `start`/`stop`、Root 禁用和“切回自动”不是同一种事件。控制模式和期望状态跨重启持久化；未知网络时保持的实际状态不能冒充已确认的联网状态。具体状态编码、持久化原子性按 D-024/AC-021；IPC 字段与 v2 契约已见第 8 节 Q-009。

| cgroup/taskset 不可用 | 性能设置假成功 | 可选降级/warnings；不阻断核心；设备验证 |
| TUN/eBPF/ipset 差异 | 规则失败/网络中断 | 能力探测、事务回滚、六模式设备矩阵 |
| WebUI 旧契约 | 页面/任务不可用 | v2 类型/测试、旧 box.tool 不静默适配 |
| 常驻功耗/唤醒 | 耗电回归 | Q-008 实测；不宣称省电 |
| settings/token 重置不可逆 | 用户配置丢失 | root-only 备份、显式提示、D-019/D-022 |

- 回滚：事务内回滚 `last_good`；切换前保留 2.0.0 shell/数据备份；daemon 失败由服务管理器重启，不与 shell 控制器并行；回滚失败进入 manual，不无限重试。
- 发布门禁：AC-013/AC-014（完整路径与设备矩阵）、AC-020–AC-024 的证据、Q-002/Q-004 阻塞项关闭、文档同步；否则只做内部试点。
- 1.4.0→2.0.0→Rust 直接升级路径必须在隔离夹具覆盖备份/重置/中断恢复；不能只测全新安装。
